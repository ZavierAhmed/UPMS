# P3.2B1 schema, guards and recovery impact

No new DDL, migration, master seeding or guard changes are needed relative to P3.2A. No SQL was executed on GoDaddy. The five-table P3.2A plan, normalized schema hashes, four configurable master definitions, schema receipt and fifteen guards remain byte-for-byte unchanged. The baseline twenty tables/original forty-five guards are unchanged. Isolated acceptance installs the existing plan into a fresh loopback fixture and verifies twenty-five tables and sixty exact guard definitions.

## Why the existing schema suffices

`money_batches.source_type` is varchar(32); DOCUMENT is a reserved application namespace alongside OPENING/TRANSFER/EXTERNAL/REVERSAL. SOURCE_CREDIT/SOURCE_DEBIT already express one-legged business receipts/disbursements. `source_key` stores the canonical document-ID hash under the existing unique source claim; source_ref retains the readable ID. Account/actor/batch/movement/audit foreign keys remain intact. Server-owned integration/account fields fit the existing immutable JSON business snapshot; no historical snapshot is rewritten.

The document relationship is validated in both directions by application reconciliation. It is not a new SQL foreign key from the hashed source identity to `v1_documents`. The runtime still has only SELECT/INSERT/UPDATE/DELETE in the synthetic acceptance fixture. No new runtime administrative, wildcard, table, column or grant-option privilege is required. The original strict scoped hosting policy and GoDaddy CRUD policy were not modified. A future deployment on a strict scoped host would need a separately reviewed versioned extension of its allowlist/grants for the five money tables; this milestone does not claim that the legacy scoped verifier already accepts new-table grants.

## What the database guards do and do not enforce

Existing fifteen money guards deny runtime modification/deletion of posted batches, movements and audits, prohibit runtime account/master receipt changes, validate basic movement shape and audit actor/reason/time, and prohibit non-opening cheque-custody effects. Existing forty-five rules continue protecting original posted business history. Local negative SQL tests exercise mutation denial and failed DDL/GRANT using the actual authenticated four-privilege runtime. The complete sixty-rule manifest is verified on encrypted restore. Test maintenance uses a separate local identity; its definer privileges are explicitly **not hosted least-privilege acceptance**.

The guards do not authenticate a source document or enforce cross-table business/money completeness at transaction commit. A holder of compromised runtime SQL credentials can still fabricate otherwise valid new inserts, invent compatible source/claim/audit sets, or manipulate unprotected mutable state within the previously documented residual model. In particular the original reversal shape guard does not understand the new DOCUMENT namespace; the API and reconciliation prohibit detached reversal, but this is not claimed as database-enforced source isolation. Existing immutable rows remain guarded; application authorization and consistency checks are not equivalent to database-enforced provenance or row isolation. No guard was silently weakened to add this adapter.

## Recovery and future migration boundary

The P3.2A `UPMS_MONEY_SNAPSHOT_V1` local prototype already serializes all twenty-five table rows and sixty trigger definitions, so DOCUMENT claims require no new archive table layout. Captures now identify `documentIntegrationVersion=p32b1`. Restore additionally verifies all canonical document links, classification, source amount/date/direction and posting actor after authenticating/decrypting and restoring the complete data. Existing table/FK/guard/full-row comparisons remain. This was exercised only on a fresh empty positively identified local `_restore` schema. No live backup was restored or changed.

The current production collector and protected Windows consumer still expect twenty tables/forty-five triggers. They have **not** been upgraded by P3.2B1. A future release must implement and independently test a version-aware streaming/encrypted off-host producer/consumer and genuine restore before any hosted P3.2A table installation. Deployment of P3.2B1 alone with feature off does not migrate production; enabling it without the full schema/evidence fails closed. The future release approval also requires explicit p32b1 integration version, genuine recovery evidence, target-bound guard/runtime proofs and owner approval. No approval receipt or hosted verification was invented.
