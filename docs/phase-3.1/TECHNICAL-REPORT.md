## Behavior

Reports now includes **Hafta Report**. Each client has an approved Unique Plastic Industry logo, date range, DAY/DESCRIPTION/QTY/RATE/AMOUNT rows and a separate financial summary. Wide screens use four columns; A4 landscape uses two, A3 landscape four. Dates default to the Pakistan-local Monday–Sunday week. A date picker selects the week containing a chosen date; From/To override it. Clients can be all or selected using a searchable checkbox list. Empty selections/weeks, loading states and API errors are explicit. Selection/date/paper state is stored in the URL. Print uses the current report and selected paper through the browser's Print / Save as PDF flow.

`GET /api/v1/management/simple-v1/hafta?from=YYYY-MM-DD&to=YYYY-MM-DD&parties=1,2` shares the existing authenticated designated-administrator policy and mandatory password-change gate. Unknown filters, invalid dates, reversed/over-366-day ranges, malformed party IDs and vendor IDs are rejected. It has no write operation. `HaftaReport` reads posted documents, immutable line snapshots, client parties and party journals; it never reads current item prices for historical sales. Integer-cent arithmetic uses the existing Brick/Math and Exact helpers. Missing/mismatching line totals or journal movements fail closed. No DDL or additional privileges are needed.

The report service issues SELECTs only. Normal authenticated middleware still touches session expiry; the no-write integration check fingerprints all non-session tables, including financial records, audit and idempotency records. Report generation creates no financial/audit/command entries.

Item Name reuses `description`; Quality, Colour and Packing accept omitted/blank values, Remarks and Selling Price remain optional. Blank price is SQL NULL, not a free selling rate. Existing positive-rate, version-review and pricing rules remain. Item codes are still generated by the existing protected counter, are unique and immutable. Identical/similar names are not merged. An omitted optional PATCH field preserves its saved value, while an explicit blank clears it; an omitted selling price preserves the existing price. Posted snapshots remain untouched.

Items and Reports have Back buttons. Item detail/edit navigation carries list search context. Item drafts remain cached during in-app navigation; leaving an edited item requires confirmation, and closing/reloading warns through the existing unload guard. Signing out explicitly confirms discarding cached drafts. Browser Back restores URL-based report filters; no item draft is silently deleted by navigation.

## Financial definitions and source limits

| Field | Exact meaning |
|---|---|
| Gross sales | Sum of posted challan line amounts in the selected date range, from historical snapshots. |
| Discounts | Recorded challan bill discount, once per document, not once per line. |
| Returns credit | Posted return line credits, including returns against earlier-week challans. The original rate is retained; AMOUNT is the recorded allocated net credit after the original bill discount, so return QTY × gross RATE need not equal net credit. |
| TOTAL | Gross weekly sales − recorded bill discounts − posted return credits. This can be negative in a return-only week. It is not an outstanding balance. |
| Receipts / reversals | Full posted client receipts and separate reversals in this week. Receipt method/reference is preserved. A cheque receipt is credited according to existing V1 policy; a dishonour contributes its own reversing movement. Neither is silently allocated to this week's invoices. |
| ADVANCE | **Not classified**, not zero. PHP V1 does not record advance allocation separately from ordinary account receipts. |
| Opening | Signed journal balance before From, available only when the client flag and an explicit posted opening/journal before From establish coverage. A missing opening is never treated as zero. |
| Opening entries / corrections | Separate signed journal movements from explicit opening/correction documents inside the selected range. These are not sales. |
| BALANCE | Verified opening + all signed journal movements through To. Negative means company owes the client. If beginning-of-range coverage is unverified, BALANCE is unavailable and a warning remains visible on screen, PDF and Excel. Prior recorded movements are available as evidence, not asserted as a complete balance. |

PHP V1 has no dedicated customer COLOR AND DIE CHANGE charge field or supported posting kind. Free-text remarks and unrelated business expenses cannot establish a receivable charge; none is fabricated. No such row is printed without a supported source. The schema also has no separately recorded GST/non-GST classification: this is stated on each block, clients are never mixed with vendors, and recognized classified document payloads cause a review-required error instead of being combined.

The separate name/amount summary in the unavailable sample cannot be assigned an unambiguous meaning. The current sources support each client's net sales, receipts and verified balance, but these are different measures. The implementation supplies those labelled per-party totals rather than guessing a separate summary metric. No conversation images were assumed to exist; layout follows the supplied text and the existing approved logo/design language.

Owner clarification for a later milestone:

1. Should the separate name/amount summary represent net weekly sales, receipts, advances or verified outstanding balances?
2. How should explicitly allocated advances be recorded and applied? Existing ordinary receipts cannot answer this.
3. What authorized document/journal operation should record color/die charges, including discount/tax treatment?
4. Should an opening posted on From count as beginning-of-day coverage? This implementation conservatively requires evidence before From and warns for an opening first recorded inside the range.
5. If GST separation is required, define its explicit source model and opening migration; do not infer tax class from names or remarks.
