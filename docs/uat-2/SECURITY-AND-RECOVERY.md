# Security and isolated recovery

`UPMS_CHEQUE_MANAGEMENT_ENABLED=false` is the default. Enabling it is insufficient: readiness requires the positively pinned local CLI MariaDB engine, the cumulative schema, a maintenance-created native-definition proof bound to the target/authenticated runtime and all guard-plan hashes, and the exact visible trigger-name set. Production profiles are rejected. There is no hosted installer or production approval bypass.

The CRUD runtime cannot read trigger bodies. The maintenance verifier reads and compares every original/additional definition and definer; runtime verifies the protected proof and visible names. Readiness is cached only within the same HTTP request/connection. A privileged maintainer who changes a trigger body while preserving its name can invalidate that proof's assumptions; runtime metadata visibility cannot independently discover that. Privileged changes require a new maintenance verification and release review.

Synthetic authenticated-account tests verify SELECT, INSERT, UPDATE and DELETE on the target, no target DDL and native UPDATE/DELETE rejection. The local test engine also has inherited PUBLIC grants on unrelated disposable `test`/`test_%` namespaces; these are not changed or represented as production privilege evidence. This milestone neither connects to nor verifies GoDaddy grants.

Existing posted financial journals, history and audit protection remain under the original 103 definitions. The new 21 guards protect additional custody/history/claim rows and constrain relevant inserts. They do **not** establish SQL row isolation or prove physical funds. Compromised runtime SQL credentials can read full stored drawer identity and may fabricate mutually consistent authorized-looking inserts, modify existing mutable control/stock/session/password fields allowed by the older model, or cause denial of service. Application authorization is not equivalent to database-enforced immutability or independent approval.

The seven cheque permissions, designated operator, enabled account, mandatory password change, session expiry, CSRF, Origin, idempotency and transaction checks remain enforced. Browser previews use strict loopback Host/Origin rules and a distinct HttpOnly/SameSite=Strict `upms_cheque_uat` cookie, separate from the owner Employee Hafta preview. The real PHP boundary continues to use its Secure `__Host-upms-php` cookie internally.

Recovery format: `UPMS_INCOMING_CHEQUE_CLEARANCE_SNAPSHOT_V1`, exactly **44 tables / 124 guards**. It includes instruments, all events, audit hashes, clearance claims, source/payment/journal/money evidence, identity and cumulative prior schema. It uses the existing authenticated sodium sealed-box encryption, never records private key material and independently restores into a new empty `_restore` database. Canonical DDL, manifest versions, exact table/guard sets, FK consistency, row equality and financial/lifecycle evidence are checked. Older consumers reject this format; it cannot be mislabeled as the 38-table snapshot.

`evidence/recovery.json` records real capture, authenticated decryption, independent restored rows, native guards and rejection tests. Corrupt ciphertext, wrong recipient, missing sources/events/audits/commands/opening journals, altered instrument/state, duplicate claims, incompatible version and altered DDL must fail. Older financial consumers also reject retained new cheque markers/receipts if an archive is retagged and its new tables stripped. Rejected manifests/DDL are tested before any restore writes.

The collector, scheduler, DPAPI recipient, protected off-host backup script and production settings are unchanged. Existing production backups still cover their existing 20-table/45-trigger deployment and do **not** support UAT-2. Hosted activation stays blocked until an independently approved upgrade provides protected off-host backups for the exact new cumulative format and a genuine independent restore succeeds. A local synthetic restore is not hosted recovery readiness.
