# Proposed P3.2B3 — integrated financial corrections

This is a separate proposed milestone, not implementation or deployment authorization. P3.2B2 adds no payment, expense or settled-purchase correction endpoint. Existing integrated payment reversals are blocked; standalone money reversals cannot target a DOCUMENT claim. An employee/category rename never reverses, edits or reclassifies an old expense.

Before implementation, approve source eligibility, full/partial correction limits, dated cutoff/backdating policy, accounting convention, reason/evidence, actor roles and independent approval. Define expense correction versus replacement, original/updated category/employee snapshots, paying account, funds availability and related tax/report treatment. Define settled purchase corrections together with stock availability, vendor payable and exact refund/payment evidence. A challan return or vendor credit is not automatically a cash refund.

Every approved correction must preserve the immutable original and link one canonical correcting business fact with the exact opposite/adjusting money effect, party/stock effects where applicable, audits and idempotency command in one existing transaction. Require uniqueness, concurrency protection, no negative spendable balance, no detached standalone money reversal and source/effect reconciliation in both directions. Posted report totals must explain originals/corrections without silently deleting a historical expense or creating a second settlement.

Test duplicate/concurrent correction claims, insufficient funds, stale sources, unauthorized actors, stock/party/money/audit/command failures, retries/uncertain commits, exact reports and genuine encrypted recovery. Introduce a separately versioned schema/guard/backup extension if needed; do not weaken any of the existing 72 rules or historic snapshots. Employee advances and loans need their own explicitly approved accounting model, not expense corrections or negative expenses.
