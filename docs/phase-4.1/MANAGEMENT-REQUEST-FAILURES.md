# Management request failures

P4.0 captured generic request-error banners on Challans, Vendors and Cheques at 768 px while layout assertions passed. That run did not record status, method or request reference for the failures. A CSS diagnosis is unsupported.

The focused Chrome runner uses the existing isolated PHP bridge and synthetic 47-table/133-guard fixture. It records failed API methods, paths without query strings, HTTP statuses, safe error codes and request IDs when supplied. It runs real Chrome at 390, 768, 1024, 1440 and 1920 px. The report treats any captured failure or banner as a failed run. PHP readiness must pass before opening the browser. Existing role and origin controls apply.

A clean rerun alone cannot explain the earlier intermittent failures. Compare request evidence and verify filters, loaded rows, valid and expired sessions, CSRF and navigation before closing functional acceptance. Do not relax application permissions or infer a root cause from viewport width.

The captured baseline recorded 31 GET responses with HTTP 503 IDENTITY_UNAVAILABLE, five at 390 px and 26 at 768 px. The same Chrome run completed the other widths without those failures. The concurrent seven-request workspace loader contends for the database identity_guard row. Local PHP logs during the reproduction include PDO HY000/1205 lock waits. No 401 or 403 was observed in the failed batch. The baseline response omitted the private log's request UUID, so individual pre-fix failures cannot all be paired to their exceptions. Source now sequences workspace reads and stops stale navigation before launching additional reads. A server-generated X-Request-ID is forwarded by the test adapter and surfaced in the workspace error UI. Existing locks, permission checks and write/idempotency behavior are preserved.

The post-change 60-case Chrome run captured zero HTTP errors or generic banners on Challans, Vendors and Cheques across all five widths. Mobile navigation and reduced motion passed. The overall run still failed one case on Money Accounts at 1920 px: GET /api/v1/management/simple-v1/documents returned 503 IDENTITY_UNAVAILABLE. Request ba43c38b-8f03-431b-a8a1-8e86cfcc439f matches an isolated PDO HY000/1205 lock wait. A separate browser run shared this fixture during that window, so cross-session contention remains possible. This result verifies the original three surfaces in the run and keeps the broader functional gate open.

The focused 768 px run passed filter entry and clearing on all three pages, with no unsafe HTTP methods or HTTP failures. The fixture returned empty challan and vendor lists and 32 cheque rows. Clearing the cheque filter restored all 32 rows. The first filter attempt failed to restore the rows after an ambiguous text selection, and the next attempt used an unsupported Puppeteer keyboard method. Both logs were retained locally. The final runner uses the installed keyboard API, checks the cleared URL filter, and waits for the original row count to return.

A standalone Money Accounts retry at 1920 px passed with no HTTP error, banner or unsafe request. Keep the original correlated failure in the release evidence. The retry does not establish production concurrency acceptance.

A separate read-only Chrome pass on the fresh isolated financial fixture exercised nonempty Challans and Vendors lists at 768 px. The no-match filter produced zero rows and clearing restored four challans and one vendor. The original fixture was independently checked at 47 tables and 133 guards with /readyz 200, session 200, matching CSRF and an administrator role. These fixture checks contain no credentials.

The final single-session run passed all 60 viewport and route cases, Back and Forward navigation and reduced motion. It captured zero HTTP failures, zero alerts and zero unsafe requests.
