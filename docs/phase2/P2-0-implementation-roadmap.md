# Proposed implementation roadmap after P2.0

**PROPOSED only. Do not begin any stage under this milestone.** Each stage requires a separately approved scope, branch, tests and independent review. A green public-website test suite is not business-system acceptance or production readiness.

## Dependency corrections to the suggested order

Durable sessions cannot safely precede every database foundation, so P2.1 should include a narrowly approved identity/session schema foundation or explicitly use a nonpersistent shell prototype with no production authentication claim. Prefer the former only after database access/hosting decisions and explicit implementation authorization. P2.2 then completes shared business controls and masters.

Approvals, stock adjustments and opening protection cannot all wait until P2.7/P2.8: earlier financial/stock postings depend on exact-version approvals, cutoff/period checks, correction extensibility and invariant guards. Build those shared controls before releasing dependent ordinary posting, while their detailed UIs can come later. Purchases with immediate payment depend on money accounts/vendor settlements earlier than P2.6; P2.4 must include that minimum Accounts foundation. Opening **design/guards** are early prerequisites even though verified production cutover comes last.

| Stage | Proposed deliverable | Preconditions / independent exit gate |
| --- | --- | --- |
| P2.1 Identity, roles and private shell | Explicitly authorized minimum MySQL identity/session foundation, maintained hashing/CSRF, login/logout/revocation, backend permission and column-scope framework, isolated private React shell | Approve P2.0/P-07/Q-14/Q-17 and actual DB access scope; no public data leak, session fixation or stale privilege; no sales/stock features |
| P2.2 Shared MySQL foundation and masters | Reviewed schema/migrations for business headers, policies/period/cutoff, durable idempotency, numbering, atomic posting coordinator, audit/approval controls; units/categories/variants/parties/accounts | Resolve Q-01/Q-02/Q-09/Q-10; test concurrency, transactions, money/stock rules, rollback and grants; no startup auto-migrations |
| P2.3 Inventory, production and consumption | Stock journals/caches, independent finished production and material consumption; approved inventory adjustment/inspection groundwork | Shared controls complete; resolve Q-13/Q-19 and opening/count test basis; concurrent all-category no-negative tests; no BOM/valuation |
| P2.4 Purchases and vendor balances | Received purchases, vendor payable/settlements; minimum money account journal and exact deficit-approval path for atomic immediate payment | Accounts foundation cannot be postponed; resolve received-invoice timing, settlement limits and Q-04 for any exception enabled; no double payment/expense |
| P2.5 Challans, sales and separate ledgers | Direct authorized dispatch/sale posting, manual rate/GST, immutable customer GST/NON_GST journals; print only after visibility/template decision | Q-05/Q-06/Q-09 resolved as needed; no stock/sale partial commit; taxpayer/invoice compliance reviewed separately; posting-number tests |
| P2.6 Customer receipts, allocations and cheques | Single-credit receipts, partial/later allocation events, transfers/custody/clearance/dishonour with per-instrument policy; expanded account UI | Q-07/Q-12/Q-21 decisions; two-policy and opening-recognition tests; no duplicated cash/customer credits; money exception exactness |
| P2.7 Returns, corrections and expenses | Physical receipt/quarantine, inspections, reusable/damaged disposition with separate credit valuation, linked challan corrections, general expense workflow | Q-03/Q-11/Q-20 plus relevant receipt/tax policies; approvals already exist; cumulative correction/return/allocation races and physical-evidence tests |
| P2.8 Opening dry runs, reporting and reconciliation | Private staged mappings, verified cutoff/opening/cheques, operational reports/export security, cache/journal/control-total reconciliation | Q-08/Q-15/Q-16/Q-18/Q-22/Q-23 resolved; isolated restore/dry-run signed off; no bulk historical source import; real cutover separately approved |
| P2.9 End-to-end validation and deployment preparation | Role/department/security/performance/resilience/invariant testing, hosting-edge acceptance, backups/restore drill and rollback rehearsal | All enabled workflows' policy gates closed; eligible hosting and verified proxy/DB limits; no live deploy or SMTP activation without explicit release approval |

Resolve only decisions relevant to a stage before that stage; unresolved return/cheque policies can keep those paths disabled, but may not be silently guessed. Earlier milestone implementations must define safe interfaces for later corrections and retain original histories, not claim incomplete correction paths are production-ready.

Test with synthetic parties/items/amounts, not imported customer records. Verify public W06 regression on every later stage. Stage schema changes must be reviewed and explicitly applied with dedicated migration privileges and rollback/forward-fix plans. Never allow an incomplete opening generation or a partially implemented financial module to affect live operations.

Deferred beyond V1: payroll/advances, automatic BOM/unit conversion, costing/valuation/COGS, full general ledger/statutory reports, microservices/permanent workers and automatic historical transaction imports. Owner approval of this roadmap authorizes planning order, not the next implementation; request a separate P2.1 instruction after P2.0 review.
