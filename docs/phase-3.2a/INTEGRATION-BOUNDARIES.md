# Receipts, payments, expenses and Hafta boundaries

Current PHP source audited: `Documents`, `MasterData`, `BusinessCommand`, `Pricing`, `ChallanReturns`, `SimpleV1::ledger/register/overview`, `Reconciliation`, `HaftaReport`, `PaymentDocument` and the current Simple V1 forms. Older Node Phase 2 modules were reviewed only as business documentation; no old Node money routes or schema were ported into production functionality.

Money Accounts is a separate immutable ledger. It does not write `v1_documents`, party/stock journals, stock quantities, revenue or expense records. Existing protected `v1_commands` supplies the same actor/fingerprint/idempotency protocol; money audit is in its own table. Current PHP transactions serialize through `identity_guard`, and account rows are also locked in numeric identity order. Exact available funds and reconciled evidence are rechecked inside the same transaction before any debit. Account dates are nondecreasing to prevent a backdated debit from inventing historical availability.

| Existing operation | Current behavior retained | Later integration contract |
|---|---|---|
| `CLIENT_PAYMENT` cash/bank | Account-level client credit, official CR identity and immutable party snapshot/journal; no money-account allocation. | P3.2B must require a verified compatible money account and atomically claim the actual posted V1 document ID once for a money credit, in the existing outer transaction. A failure must roll back both party and money effects. Never post a second client credit or infer an advance. |
| `VENDOR_PAYMENT` | Vendor payment debits/reduces the party payable; method/reference is not a holding balance. | P3.2B adds one verified cash/bank debit against that document identity with an insufficient-funds check, without changing the existing party convention. |
| Paid-immediately `PURCHASE` | Existing stock acquisition and existing net vendor effects are unchanged. | Claim its posted source once for one money debit. Do not create an additional vendor payment or double-count paid purchases. Credit purchases have no immediate money effect. |
| Paid `EXPENSE` | Existing category/payee/amount and PAID-only validation; no money account today. | P3.2B adds a required verified cash/bank source and one money debit in the same expense-post transaction. P3.2D can add employee/category identities separately. Do not reclassify an internal transfer as expense. |
| Cheque `CLIENT_PAYMENT` | Existing V1 credits the client on cheque receipt; reference and dishonour reversal are retained. | P3.2C must explicitly model instrument identity, custody/deposit/clearance/dishonour and money recognition. Receipt into custody must not credit spendable cash/bank. Define exact clearing and reversal policy first. No ordinary custody transfer exists in P3.2A. |
| Existing `PAYMENT_REVERSAL` | Only the supported original cheque-dishonour correction changes its existing party position. | Link to the original instrument/money effect when implemented; do not infer cash outflow for a cheque that never cleared. Use a unique correction claim and immutable opposite entries. |
| `CHALLAN` / `CHALLAN_RETURN` | Sales, bill discounts and allocated net return credits retain immutable snapshots and party effects. | No automatic money movement: a sale/credit is not a receipt/refund. A future actual refund requires its own authorized source and funds check. |
| Internal money transfer/reversal | Equal opposite legs in two cash/bank accounts; reversal links to and preserves the original. | Always money-only. No party credit, income, sale, expense or stock movement. Bank fees, if later supported, require a separate evidenced expense. |

The current external-source API accepts an explicitly verified, justified administrator attestation with a unique normalized reference. It is for independent external money evidence only. It rejects references matching existing V1 official/external/cheque references rather than silently treating a posted V1 record as newly linked. This is not a complete legacy linking or allocation workflow and cannot detect every human alias for a physical source. Future source adapters must reserve a canonical namespace keyed by actual document identity, reconcile existing external claims before any approved historical linkage, and never automatically backfill balances from payment-method labels.

Hafta is unchanged. It reads only existing posted challans/return snapshots, receipts/reversals and party journals. Money transfers, declared custody values and external funds neither appear as Hafta sales nor as ADVANCE. Opening coverage, warnings, exact discounts/returns, grouped exports, item-name-only entry and Back behavior remain covered by the P3.1 unit/component and isolated integration tests.

Outstanding policy decisions before later implementation: per-account operator restrictions or dual approval; documentary opening evidence/cutoff and opening corrections; permitted external source categories and independent verification; bank fees/reconciliation rules; cheque instrument migration and when spendable bank recognition occurs; account closure/renaming governance; and any approved historical linkage. No deficit exception, partial reversal or automatic adjustment is implemented.
